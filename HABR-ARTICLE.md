# Перевёл каталог аниме с Node.js на Rust: 12 багов, которые нашлись только при переносе

*Пять месяцев назад я написал каталог аниме на Node.js. Он работал, отдавал JSON API,
в нём было 20 000 записей из трёх источников и веб-интерфейс. Потом я переписал его
на Rust, и выяснилось, что половина функций никогда не вызывалась, а ключ в базе
гарантированно терял данные. Ниже — не «почему Rust лучше», а что конкретно сломалось
и что с этим делать.*

Репозиторий: [github.com/TeivrimOriginal/TeivrimSite](https://github.com/TeivrimOriginal/TeivrimSite)

## Что это за проект

Каталог аниме, который агрегирует три публичных API в одну базу:

```
AniList   (GraphQL)  ─►  названия, оценки, связи, рекомендации, теги
Kitsu     (JSON:API) ─►  оценка 0..100, персонажи, озвучка, создатели
Shikimori (v1 JSON)  ─►  русские названия и описания
                    ─►  SQLite + FTS5  ─►  JSON API + веб-UI + Android-клиент
```

Масштаб: ~20 000 записей, 115 файлов (из них 32 — сам сервер на Rust),
22 коммита в текущем виде.
Языки по объёму: Rust — 666 КБ, Kotlin (Android) — 158 КБ, JavaScript (фронтенд) —
80 КБ, PowerShell (сборка и публикация) — 37 КБ.

Один origin на веб и Android — это осознанное решение, а не экономия: приложение
не хранит каталог у себя, поэтому исправление в базе доезжает до всех установленных
клиентов без публикации в сторе.

## Почему вообще переписывать то, что работает

Честный ответ: потому что я хочу этим заниматься. На Node.js я умел писать, но не
умел проектировать — и самый быстрый способ научиться проектированию это сменить
язык, в котором привычки не сработают. Версия 1 была написана за несколько недель
и ни разу не перечитана.

Стоило ли того — в конце поста.

## Ошибка №1: первичный ключ, который стирал данные

Это единственная ошибка, из-за которой часть каталога просто отсутствовала,
и её нельзя было заметить ни в логах, ни на странице.

В версии 1 таблица была keyed на `anilist_id INTEGER`. Идея для записей, которых
нет в AniList, была такая: взять id из того же диапазона со знаком минус.
Импорт шёл через `INSERT OR IGNORE`.

Что происходит: запись MyAnimeList с номером 21 и запись Shikimori с номером 21 —
это разные аниме. Оба получали `-21` или `21`, `INSERT OR IGNORE` видел конфликт
по первичному ключу и **молча выбрасывал вторую**. Не ошибка, не лог, не 500 —
просто запись, которой нет.

Сколько данных терялось, я не знаю: считать пришлось бы по базе, которую уже
переписали. Но потеря была систематическая, а не разовая.

Исправление — вынести источник в само имя ключа:

```rust
// uid — строка, не число. Три источника живут в трёх разных
// пространствах номеров, и префикс делает коллизию невозможной.
match source {
    Source::AniList => format!("al:{id}"),
    Source::Kitsu   => format!("ks:{id}"),
    Source::Shiki   => format!("sh:{id}"),
}
```

Побочный эффект оказался важнее самой правки: Kitsu-запись с маппингом на AniList —
это **не новая строка**, а `al:<id>`, в которую Kitsu доливает оценку и актёров.
То есть префикс заодно решил задачу слияния источников, которую в версии 1
пришлось бы решать отдельно.

## Ошибка №2: русский поиск не работал вообще

Никогда. Не «медленно», не «не находит часть запросов» — не работал.

Причина в одной строке: поиск шёл через `LIKE`. SQLite приводит регистр в `LIKE`
**только для ASCII**:

```sql
SELECT * FROM anime WHERE title_ru LIKE '%атака титанов%';
-- находит: «Attack on Titan»   (a-t-t)
-- не находит: «Атака титанов»   (А-т-а) — кириллица не свёрнута
```

Для каталога, где треть записей названа по-русски, это была мёртвая функция.

Решение — FTS5 с токенизатором `unicode61`, который сворачивает регистр для всех
письменностей:

```sql
CREATE VIRTUAL TABLE anime_fts USING fts5(
    title, title_ru,
    content = 'anime',
    tokenize = 'unicode61'
);
```

Отдельно обработан деградационный случай: если SQLite собран без FTS5, индекс не
создаётся, в лог пишется предупреждение, поиск переключается на `LIKE`-сканы.
Хуже для кириллицы, но работоспособно.

## Ошибка №3: карточка аниме показывала почти ничего

`api.rs` отдавал `SELECT *` — то есть колонки `genres_json`, `tags_json`,
`relations_json`, `studios_json`. А `detail.html` обращался к `genres`, `tags`,
`relations`, `studios`. Ни одно из имён не совпадало, поэтому все секции карточки
выходили пустыми.

Вдобавок проверка существования шла по `a.id`, а колонка называется `anilist_id`.

Обе проблемы исчезают, когда контракт описан в типах, а не в соглашении между
SQL-строкой и шаблоном:

```rust
// Компилятор не даст собрать хендлер, если поле переименуют
// в структуре и забудут поправить здесь.
#[derive(Serialize)]
pub struct AnimeDetail {
    pub uid: String,
    pub title: String,
    pub genres: Vec<Genre>,
    pub studios: Vec<Studio>,
}
```

## Ошибки №4–№5: код, который не выполнялся

`load_jikan` и `translate_pending` **не вызывались ниоткуда**. То есть оценки MAL,
персонажи, озвучка, создатели, темы, синонимы и машинный перевод были недоступны
принципиально — не «иногда ломались», а никогда.

`Jikan` заменил на `Kitsu`: он отдаёт те же данные, у него есть внешние id для
сведения записей, а его оценка `0..100` совпадает по шкале с AniList. Аналогично
ушёл переводчик через Google — он приводил к бану IP.

Второе — загрузчики стартовали по `sleep(30)` и `sleep(120)` от старта процесса.
Это гонка, а не задержка: на уже прогретом прогоне сопоставление жанров видело
таблицу, которую ещё никто не наполнил. Сейчас стадии идут последовательно:

```rust
load_anilist().await?;   // задаёт множество строк
load_kitsu().await?;     // присоединяется по внешним id
load_shikimori().await?; // присоединяется по названию
```

## Ошибка №6: фильтр по агрегату в неправильном месте

```sql
-- было: misuse of aggregate
SELECT g.id, count(a.uid) FROM genres g JOIN anime_genres a ON ... WHERE count(a.uid) > 5

-- стало
SELECT g.id, count(a.uid) FROM genres g JOIN anime_genres a ON ...
GROUP BY g.id HAVING count(a.uid) > 5
```

Список жанров не работал **никогда**.

## Ошибка №7: двадцать `CREATE INDEX IF NOT EXISTS` на каждый HTTP-запрос

Каждый запрос списка открывал соединение и выполнял `ensure_schema()` — то есть
двадцать `CREATE INDEX IF NOT EXISTS` заново. Схема применяется один раз при старте,
соединения берутся из пула.

## Ошибка №8: заведомый 429 от AniList

Лимит AniList — 30 запросов в минуту. Загрузчик ждал по 750 мс между запросами,
то есть отправлял 80 в минуту. `Retry-After` не обрабатывался.

Запросы теперь темпяются по квоте с уважением `Retry-After`. Заодно выяснилось,
что `ANILIST_CLIENT_ID` поднимает лимит с 30 до 90 — самый дешёвый выигрыш во всём
проекте, три минуты настроек против часов импорта.

## Ошибки №9–№11: тихие поломки

**Жанры и поисковый индекс появлялись только в конце импорта.** Импорт идёт
несколько часов, и всё это время поиск был пуст. Сейчас оба обновляются
**постранично**.

**Список пользователя возвращался пустым.** Join с `favorites` не проецировал
колонки списка, поэтому каждая строка падала, а ошибки молча проглатывались.

**Пагинация Shikimori определялась эвристикой** `items.len() >= 40` при запрошенных
50, из-за чего импорт обрывался раньше времени. Теперь берётся `meta.total` из ответа.

## Ошибка №12: оценку нельзя было очистить

Это мой любимый класс багов — ошибка, которую не видит ни компилятор, ни ответ
одного запроса.

```rust
// Option<Option<T>> в serde разбирает И отсутствующее поле,
// И явный null в одно и то же None.
score: Option<Option<f32>>,
```

Клиент физически не мог сказать «убери оценку»: сервер не отличал «не передано» от
«передано null». Разбор вынесен в отдельный десериализатор, который различает
эти два случая, а кодировщик на клиенте пишет `null` явно:

```kotlin
// Две конфигурации, намеренно противоположные.
val decoding = Json { explicitNulls = false }  // сервер добавил поле — клиент выживет
val encoding = Json { explicitNulls = true }   // PATCH: null означает «очистить»
```

Общая конфигурация здесь ломает семантику PATCH: «поле отсутствует» значит
«не трогай», «null» значит «очисти». Одна конфигурация на оба направления —
и очистка оценки молча не сработает.

## Что дал именно Rust

Три вещи, которых в Node.js не было и которые не про синтаксис.

**`rusqlite` синхронный, а Actix — асинхронный.** Забыть об этом — значит повесить
рантайм на каждом запросе к базе:

```rust
// web::block уводит блокирующий вызов с async-воркеров
let row = web::block(move || {
    let conn = pool.get()?;
    query_optional(&conn, &sql, params)
}).await??;
```

**Поле сортировки интерполируется в SQL, а не биндится.** Значит, оно обязано быть
whitelist, и это теперь видно в типах, а не в комментарии.

**Контракт с Android стал явным.** Карточка принимает интерфейс `CardData`, а не
конкретный тип `AnimeSummary`, поэтому строка каталога и строка списка рисуются
одной карточкой. Наследование или конверсия означали бы либо дублирование
дюжины полей, либо пересборку summary на каждую строку.

## Что Rust не дал

Честно, чтобы не выглядло рекламой:

- **Скорость не изменилась.** Узкое место — не код, а лимиты публичных API и
  количество данных. Импорт занимает часы при любом языке.
- **Часть ошибок пришлось нести руками.** CORS, статика и пул соединений
  заменены собственными реализациями (~200 строк) — иначе сборка тянула бы OpenSSL
  и не работала офлайн. Это была не оптимизация, а требование.
- **Сборка в RuStore — PowerShell.** Подпись RSA-SHA512, черновик, загрузка AAB,
  commit. ASN.1 разбирается вручную ради совместимости с Windows PowerShell 5.1.
  Первая версия разбора нашла две ошибки в нём самом — скрипт `test-rustore-signing.ps1`
  проверяет разбор на настоящем ключе и с тех пор ловит их до отправки.

## Итог

Двенадцать багов из списка выше я нашёл **не потому, что перешёл на Rust**. Я нашёл
их потому, что перечитал код, который сам же и написал полгода назад. Rust был
поводом.

Но если бы я писал эту штуку с нуля сегодня, я бы всё равно взял Rust для сервера
из-за одного свойства: ошибку «`Option<Option<T>>` нельзя отличить от `Option<T>`»
компилятор не ловит, а вот ошибку «в шаблоне поле называется `genres`, а в базе
`genres_json`» — ловит. Не ту, но ловит. И в моём случае обе смотрелись одинаково:
«ну вроде работает».
