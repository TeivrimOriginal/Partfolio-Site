О себе

Смотрю на план запроса, а не на глазок. В одном сервисе полнотекстовый поиск сделан через GIN поверх tsvector, причём выражение индекса и выражение запроса лежат в одной константе — специально, чтобы они не разъехались. Пагинация ограничена сверху, чтобы один запрос не вытащил всю таблицу.

Проекты

anime-sync-api — REST API каталога аниме FastAPI · PostgreSQL 16 · Alembic · GIN
  • Асинхронный стек: FastAPI, SQLAlchemy 2.0 (asyncpg), Pydantic v2, httpx. Схемы запросов и ответов разделены.
  • Три таблицы с внешними ключами и CHECK-ограничениями; UNIQUE (source, external_id) — внешний id уникален в пределах источника, потому что у AniList и Jikan нумерация разная.
  • Полнотекстовый поиск на tsvector с индексом GIN по названию, оригинальному названию и жанрам. Выражение индекса и выражение запроса вынесены в одну константу, чтобы они не разошлись.
  • Синхронизация с AniList (GraphQL) и Jikan (REST) на httpx: идемпотентный апсерт без дублей и журнал прогонов — отказ внешнего API пишется в базу, а не роняет запрос.
  • Список с фильтрами, пагинацией и полнотекстовым поиском; размер страницы ограничен сверху, чтобы нельзя было вытащить всю таблицу одним запросом.
TaskHub API — сервис управления задачами FastAPI · PostgreSQL 17.4 · Celery · Redis
  • Асинхронный сервис на FastAPI и SQLAlchemy 2.0: asyncpg, Pydantic v2, разделение схем запросов и ответов, OpenAPI 3.1 из коробки.
  • Аутентификация JWT с ротацией refresh-токенов и RBAC: роли проверяются на уровне зависимости, доступ к эндпоинту нельзя получить без проверки прав.
  • Фоновые задачи на Celery, Redis как брокер и кэш; задачи выполняются синхронно при CELERY_TASK_ALWAYS_EAGER, поэтому тесты не зависят от воркера.
